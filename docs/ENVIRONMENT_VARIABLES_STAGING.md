# Staging Environment Variable Contract

Phoenix Creator Studio staging must be isolated from production and must fail closed when required dependencies are missing.

## Secret boundary

Provider and application runtime credentials live in the **Vercel staging environment**. GitHub Actions does not receive database, Supabase service-role, Upstash token, or Auth.js secret values.

The protected GitHub Environment named `staging` receives only the automation/control-plane values needed to exercise the deployment from outside Vercel.

## Vercel staging runtime environment

### Application

- `APP_ENV=staging`
- `NODE_ENV=production`
- `NEXTAUTH_URL=https://<staging-host>`
- `NEXTAUTH_SECRET=<unique staging secret of at least 32 characters>`
- `LOG_LEVEL=info`
- `STAGING_AUTOMATION_TOKEN=<dedicated staging automation bearer token>`

### Database

- `DATABASE_URL=<serverless runtime pooler connection>`
- `DATABASE_MIGRATION_URL=<migration-safe direct connection>`
- `DATABASE_SCHEMA=phoenix_staging` (or another dedicated non-`public` schema)
- `RUN_STAGING_MIGRATIONS=true` only for the reviewed migration deployment

Runtime and migration URLs may reuse an approved retired provider account only after rotation/isolation is proven. Runtime connections use the dedicated schema. Migrations run during the explicitly enabled deployment build, never from requests or readiness probes.

### Storage

- `STORAGE_PROVIDER=supabase`
- `SUPABASE_URL=<staging project URL>`
- `SUPABASE_SERVICE_ROLE_KEY=<server-only staging service role>`
- `SUPABASE_STORAGE_BUCKET=<private staging bucket>`

`STORAGE_PROVIDER=local` is forbidden in staging.

### Rate limiting

- `RATE_LIMIT_PROVIDER=upstash`
- `RATE_LIMIT_URL=<staging shared-store endpoint>`
- `RATE_LIMIT_TOKEN=<server-only staging token>`
- `RATE_LIMIT_NAMESPACE=pcs:staging:phoenix` (or another staging-specific namespace)

`RATE_LIMIT_PROVIDER=memory` is forbidden in staging.

### Testing and recovery

- `ALLOW_REMOTE_TESTS=true` only for the reviewed isolated staging lane
- `STAGING_CONFIRM_ISOLATED=true` only after provider isolation is proven
- `FEATURE_PROJECT_RESTORE=true` for the recovery drill
- `ENABLE_TEST_AUTH_BYPASS=false`

The test-authentication bypass must never be enabled in staging.

### Optional integrations

- `OPENAI_API_KEY=<staging-scoped key>`
- `RAINSTORMS_BASE_URL=<reviewed staging endpoint>`

Optional integrations must be reported as degraded rather than silently assumed healthy.

## GitHub protected `staging` environment

### Secrets used by acceptance

- `STAGING_AUTOMATION_TOKEN` — matches the staging application's automation bearer token.
- `VERCEL_AUTOMATION_BYPASS_SECRET` — generated by Vercel Deployment Protection and sent as the `x-vercel-protection-bypass` header.

### Secrets used only by rollback rehearsal

- `STAGING_VERCEL_API_TOKEN`
- `STAGING_VERCEL_ORG_ID`
- `STAGING_VERCEL_PROJECT_ID`

The rollback API token should be fresh and limited to the staging Vercel scope where possible. It is used only to move the staging alias during the reversible rehearsal.

### Non-secret variables

- `PRODUCTION_BASE_URL`
- `STAGING_DATABASE_SCHEMA`
- `STAGING_RATE_LIMIT_NAMESPACE`
- `CREDENTIAL_ROTATION_CONFIRMED`
- `HISTORY_REVIEW_CONFIRMED`
- `ROLLBACK_REHEARSAL_CONFIRMED`

Do not copy Vercel runtime values such as `DATABASE_URL`, `DATABASE_MIGRATION_URL`, `NEXTAUTH_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, or `RATE_LIMIT_TOKEN` into GitHub.

## Validation

Before deployment, run the production-like environment validator with staging values. The staging acceptance workflow then verifies deployment identity and calls server-side provider probes through the automation endpoint. Outputs may include provider identities and boolean readiness evidence, but never secret values.
